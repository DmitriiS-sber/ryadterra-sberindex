## 2. Направление «Кластеризация»

### Цель

Выделить экономически похожие муниципалитеты России, показать изменение их групп во времени и объяснить группы как содержательные типы локальных экономик.

### Что выполнить

1. Собрать данные по муниципальным образованиям и последовательности периодов. Привести идентификаторы и периоды к сопоставимому виду.
2. Выбрать экономические признаки муниципалитетов и обосновать выбор. На странице названы расходы по категориям, покупательская мобильность, отраслевая структура занятости, средние зарплаты и другие данные.
3. Построить **динамическую атрибутированную сеть**: узел — муниципалитет; атрибуты — его экономические характеристики; ребро — степень экономической близости; сеть существует для нескольких последовательных моментов времени, например месяцев.
4. Математически задать правило построения связей и объяснить, как оно влияет на сеть и результат кластеризации.
5. Сравнить подходы к определению сходства и обосновать итоговый выбор. Организатор приводит корреляции, косинусное сходство, лаговые корреляции, DTW и расстояния как возможные варианты.
6. Сгруппировать схожие муниципалитеты и предложить математический способ отслеживания изменения кластеров во времени.
7. Оценить качество кластеризации с помощью ICVI. Перечень из правил: SW, CH, S_Dbw, AVI, AVU, MQ. Для высшей оценки в приложении 1 предусмотрен полный набор метрик и комплексный анализ; если конкретная метрика неприменима, причины нужно явно обосновать.
8. Интерпретировать группы экономически, подтвердить выводы и показать практическую пользу.
9. Наглядно представить типы территорий и их динамику.

### Критерии жюри

| Критерий | Вес |
| --- | ---: |
| Понятность методологии | 15% |
| Построение сети и атрибутов | 15% |
| Сравнение методов | 15% |
| ICVI | 15% |
| Интерпретация, ясность, воспроизводимость, обоснованность выводов | 30% |
| Инновационная визуализация | 10% |

При равенстве итоговых оценок сначала сравнивается балл за интерпретацию результатов.

### Рекомендуемый вид результата

Таблица «муниципалитет — период — кластер», описание каждого типа экономики, сравнение методов и метрик, карта типов, отображение переходов между группами и несколько разобранных примеров территорий. Эти конкретные таблицы и графики — предлагаемая упаковка, а не дополнительные обязательные форматы организатора.

Один статический кластерный анализ без сети и без временной динамики не покрывает поставленную задачу.

## 3. Направление «Прогнозирование»

### Цель

Разработать алгоритм прогнозирования потребления в муниципалитетах, совмещённый с ранним выявлением структурных изменений и возможных предстоящих шоков.

### Что выполнить

1. Подготовить временные ряды потребительских расходов СберИндекса по муниципалитетам. Можно использовать дополнительные данные Росстата и надёжных официальных публичных источников.
2. Реализовать и сравнить модели прогнозирования, включив Prophet как ориентир из задания.
3. На странице перечислены горизонты **1, 3, 6 и 12 месяцев**. Предусмотреть результаты сравнения по каждому из них и объяснить ограничения имеющейся истории данных.
4. Реализовать и сравнить несколько методов обнаружения структурных изменений; обосновать выбор итогового метода.
5. Объединить прогнозирование с ранним обнаружением изменений, показать работу на реальных примерах.
6. Рассчитать **MAE обязательно**. R² можно добавить; по п. 6.2 положения она необязательна. Без MAE баллы за критерий метрик не начисляются.
7. Для высокого балла проверить современные фундаментальные модели временных рядов, объяснив их вклад и ограничения. Это отдельный критерий на 15%, в положении он назван дополнительным преимуществом.
8. Для высокого балла интегрировать новости и объяснить согласование текстовых событий с временными рядами СберИндекса. Это отдельный критерий на 15%.
9. Показать архитектуру, сравнительные результаты, экономический смысл и практическое использование решения.

### Важное уточнение о Prophet и R²

В общем описании страницы заявлена цель превзойти базовую модель по MAE и R². Более конкретные критерии и положение уточняют: MAE обязательна, R² опциональна; превосходство над Prophet учитывается при наличии подтверждённых результатов. Приложение 2 допускает высшую оценку за обоснованное сравнение, подтверждающее преимущество Prophet. Следовательно, необходимо честное проверяемое сравнение, а не неподтверждённое обещание улучшения.

### Критерии жюри

| Критерий | Вес |
| --- | ---: |
| Понятность методологии | 10% |
| Сравнение моделей прогноза | 20% |
| Сравнение методов структурных изменений | 20% |
| Современные фундаментальные модели временных рядов | 15% |
| Интеграция новостей | 15% |
| Метрики качества | 10% |
| Интерпретация, ясность, воспроизводимость, обоснованность выводов | 10% |

При равенстве итоговых оценок сначала сравнивается балл за фундаментальные модели временных рядов.

### Рекомендации по корректной проверке

- Проверять прогноз на более поздних периодах, чем обучение, без использования будущей информации.
- Сравнивать модели на одинаковых данных, горизонтах и правилах оценки.
- Для новостей учитывать дату фактической доступности сообщения, а не только дату описанного события.
- Для раннего обнаружения показывать ложные тревоги и время появления сигнала относительно изменения. Не выдавать обнаружение по полной истории за предупреждение заранее.
- Показать вклад дополнительных компонентов: что меняется без новостей или фундаментальной модели.

Это рекомендации по качеству исследования; конкретный протокол разделения выборки и метрики раннего обнаружения в проверенных материалах не зафиксированы.

## 4. Что предоставить — обязательный комплект

| Материал | Формат и содержание |
| --- | --- |
| Код | GitHub-репозиторий с чистым документированным кодом, конфигурациями YAML/JSON для гиперпараметров и инструкцией по запуску |
| Методологический отчёт | Краткое понятное изложение на русском языке: данные, подход, проверка качества, результаты, интерпретация и ограничения |
| Представление результатов | PDF-презентация **или** интерактивный лендинг |
| Для кластеризации в презентации/лендинге | Экономическая интерпретация и визуализация итогов |
| Для прогнозирования в презентации/лендинге | Архитектура решения, сравнение моделей прогноза и методов структурных изменений, метрики и реальные примеры |

В проверенных требованиях не указаны количество страниц отчёта, количество слайдов, обязательный формат файла отчёта и ограничения размера материалов. PDF-отчёт — удобный рекомендуемый вариант; PDF прямо задан как один из вариантов именно для презентации.

Практичная рекомендуемая упаковка:

- `README.md`: цель, выбранное направление, данные, установка, запуск, ссылки на отчёт и презентацию/лендинг.
- `src/` или ноутбуки: исходный код.
- `configs/`: YAML/JSON с параметрами.
- `requirements.txt` или иной файл окружения: зависимости и версии.
- `report.pdf`: методологический отчёт.
- `presentation.pdf` либо ссылка на размещённый лендинг.
- `results/`: итоговые таблицы и графики.

Это рекомендуемая структура, а не требование к названиям файлов или каталогов. Сырые данные размещать с учётом условий их использования; в правилах есть ограничения распространения материалов организатора.

## 5. Как подать

1. Завершить проект и разместить материалы так, чтобы жюри могло их просмотреть.
2. Проверить доступ ко всем ссылкам. Ссылка на репозиторий сама по себе должна позволять оценить код; ссылки на отчёт и представление результатов также должны работать.
3. Перейти на https://sber.ru/sberindex/konkurs_sberindex#forma и заполнить заявку.
4. По п. 3.2 положения указать: ФИО, электронную почту **с российским почтовым доменом**, место работы/учёбы, специализацию, мобильный телефон, название команды при командном участии, количество участников, направление, описание проекта, ссылку на сайт или страницу проекта.
5. В описании раскрыть интерес к задаче, проблему или информацию, которую проект освещает, и её значимость; обеспечить доступ ко всему необходимому для оценки, п. 4.2.
6. Принять условия положения и дать согласие на обработку персональных данных в предусмотренных полях.
7. При командном участии **каждый участник отправляет заявку**: это прямо сформулировано в п. 3.2. Для идентификации проекта разумно использовать одинаковое название команды и одинаковую ссылку.
8. Отправить до 9 октября включительно и сохранить доступное подтверждение отправки.

Рекомендация: собрать все ссылки на одной странице проекта, например в README репозитория. Тогда жюри последовательно найдёт код, отчёт и презентацию/лендинг. Отдельный сайт создавать только ради страницы со ссылками необязательно; интерактивный лендинг — альтернатива PDF-презентации.

## 7. Другие условия, влияющие на выполнение

- П. 10.3 запрещает платные проприетарные технологии, права на использование которых требуют возмездного приобретения. Подбирать зависимости и инструменты с учётом этого условия.
- По п. 10.1 победители предоставляют Сберу широкую безвозмездную неисключительную лицензию на результат, включая код, алгоритмы и материалы, с возможностью переработки и сублицензирования.
- По п. 9.3 в течение двух рабочих дней после публикации победителей необходимо отправить организатору предусмотренные сведения о личности, ИНН при наличии, банковские реквизиты и сведения о трудовых отношениях со Сбером. Команда дополнительно предоставляет подписанное соглашение о распределении приза. Непредоставление сведений в срок лишает права на приз, п. 9.5.
- Организатор вправе обновлять положение. Перед фактической подачей нужно сверить актуальную редакцию.
